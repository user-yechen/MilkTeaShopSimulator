# Context Maintainer

为这个奶茶店 Unity 项目维护 `Assets/上下文.txt`——它是跨会话记忆全部项目状态的唯一来源。本 Skill 只有两个时机会被调用：新任务开始时读一次，功能完成后写回一次。

## 触发条件

每次接到这个项目上的新用户请求，第一件事就是**读** `Assets/上下文.txt`；每次完成了功能性工作（改了脚本、改了场景、加了新文件、解决了一个 bug）并验证通过后，最后一件事是**写回**该文件。

下面任何一种情况**不要**写回：
- 跟奶茶店项目无关的闲聊或解释性回答
- 代码写了一半还在试错、还没编译过
- 用户只是问问题没让改东西
- 读文件发现文件不存在（那是第一次，告诉用户就行，不要凭空生成一个空文件）

## 读取阶段（新任务开始）

1. 用 Read 工具打开 `Assets/上下文.txt`。如果文件不存在或读取失败，向用户报告情况后跳过本 Skill 后续步骤，继续正常处理当前请求。
2. 快速扫一遍四个关键区块，确认脑中的项目状态和文件一致：
   - **脚本功能索引** —— 16 个 .cs 文件各自做什么，有没有哪个脚本刚被改过但还没记录？
   - **场景关键事实** —— 地板拼接/Transform/fileID、奶茶机子节点、加热机子节点、路人 PrefabInstance，有没有用户新加的节点？
   - **最近 5 次对话** —— 滚动区，确认哪些历史决策是定下来的（比如"把 Y 轴锁死改成 RaycastNonAlloc"、"杯位改成场景直接引用"）
   - **经验教训** —— 踩过的坑（Unity CS0433 facade、Matrix4x4 累积、Raycast 过滤自身、场景未保存导致 FindSlot 失败等），避免在当前任务里重复踩
3. 如果上下文文件里的脚本清单和磁盘上实际的 `.cs` 文件对不上（比如磁盘上多了新的 .cs 但文件没记，或文件记了但磁盘没有），以**磁盘实际为准**更新脑中的状态，但先别急着写回——等当前任务跑完再统一写。

## 执行阶段（干活）

正常执行当前任务。中间如果产生了以下新事实，先存在脑子里，等最后一次性写回：

- **新增或修改了脚本** → 记下文件路径 + 核心改动 + 关键字段/方法签名
- **场景里出现了新的节点/物件类型** → 记下 PrefabInstance ID / Transform fileID / 关键 localPosition / 是否带 Collider
- **踩了新的坑** → 记下现象、根因、解决方式，以后别再犯
- **产生了新的已知 TODO** → 记下内容（比如"某 PourFluid 参数没调"、"某节点待用户保存场景"）
- **编译验证命令有变化** → 如果发现之前记的引用组合不够，新组合记下来

注意：执行阶段不要动 `上下文.txt`。改一半就写回等于把半成品固化进记忆，下次新会话读到的会把半成品当真。

## 写回阶段（功能完成后）

在开始写回之前，必须满足至少一个条件：
- 编译验证通过（csc 退出码 0），或
- 改的是纯数据/配置/场景文本，无编译要求，且 Edit 已落盘

写回步骤：

1. **更新脚本功能索引区块**：
   - 新增脚本要完整写功能摘要
   - 修改过的脚本只改变动那一段（比如加了新字段、改了某方法逻辑）
   - 不要把整段 .cs 源码粘进去，只写功能描述 + 关键 API
2. **更新场景关键事实区块**：
   - 新节点、新 Transform、新 Collider 都记
   - 如果旧的事实已经失效（比如"出料口还没保存"现在已保存），改成最新状态
3. **更新经验教训**：新踩的坑追加一条，和旧坑并列
4. **更新当前待做 / 已知 TODO**：新产生的 TODO 追加，已解决的删掉
5. **滚动对话记录**：
   - 把**本次对话**追加到"最近 5 次对话"区块的末尾（用 `【对话-⑥】用户】...→（我）...` 格式）
   - 如果区块里已有 ≥5 条，删掉最老的那一条（保持总条数 ≤5）
   - 只记要点：用户原话的核心需求 + 你做了什么 + 关键决策/验证结果，不要把完整对话粘进去
   - **格式**：
     ```
     【对话-⑤ 用户】提炼上下文，生成一个"上下文.txt"文件……
       →（我）创建 Assets/上下文.txt，7 大区块结构约定……
     ```
6. **整文件覆盖写**：用 Write 工具一次性写回，不要 Edit 中间某几段。这样能保证区块之间的相对顺序、分隔线格式不被破坏。
7. 写完后不用再读回来验证（Write 工具本身就是原子操作），直接继续向用户汇报本次工作。

## 反模式（绝对不要做）

- **不要把完整对话粘进"最近 5 次对话"**：只记要点。一次完整对话可能几十 KB，5 次粘进去下次读到会挤占 token，反而让真正重要的脚本索引被截断。
- **不要每次用户说什么都去写**：改代码/改场景/加文件才触发；解释性回答、闲聊、纯 bug 分析都不触发写回。
- **不要把长脚本源码粘进索引**：脚本索引用"自然语言功能摘要 + 关键 API"，不是复制粘贴 .cs 文件。
- **不要跳过编译验证就写回**：编译不过意味着当前代码可能有硬伤，写回去等于把错误记忆固化。
- **不要只 Edit 某一段而留下半成品痕迹**：比如脚本功能索引里只加了新脚本但忘了删已废弃的旧描述，下次读到会产生矛盾认知。整文件覆盖写是最安全的。
- **不要凭空新建上下文.txt**：如果文件根本不存在（第一次使用），告诉用户"需要先建立上下文.txt 再让我维护"即可，让用户决定文件内容。
